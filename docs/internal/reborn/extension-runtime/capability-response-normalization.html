IronClaw architecture proposal

Capability response normalization

One existing runtime outcome, one central processor, fewer wrappers, safe protocol defaults, and additive persistence—without credential probing or new lifecycle states.

Proposed · 2026-08-14

One response is transformed too many times

Transport is already mediated and final model output is already hardened. The unnecessary complexity is the chain of wrappers and repeated matches between dispatch and the runtime outcome.

WASM

Weak final ABI

Provider packages encode structured errors into strings because the WIT response has no typed outcome.

MCP

Protocol error as success

The JSON-RPC envelope is parsed, but the semantic CallToolResult error bit is not.

First-party

Per-handler policy

Useful details depend on which helper or handler happened to map the response.

ToolAdapter

Closest existing shape

Typed errors exist, but provider rejection, auth, and infrastructure are still not one semantic vocabulary.

Root cause

IronClaw already has the right runtime-neutral outcome. The defect is that no single owner constructs it, so success, auth, and failure are repeatedly renamed and reclassified.

Reuse the outcome we already have

The protocol default handles conventional behavior. Provider code overrides only decoding; after trusted dispatch and CapabilityHost lifecycle work, one processor produces the existing RuntimeCapabilityOutcome.

MCP default

Protocol-aware

Extension override

Provider semantics

Host facade

Always enforced

One concrete processor applies policy and returns the existing runtime outcome; no override bypasses host safety.

Abstraction rule

The processor is a concrete host-runtime module, not a trait. Add a decoder strategy trait only when two production implementations actually meet at one selection boundary.

Truthful without continuous probing

Active means configured for use. A provider rejection becomes new evidence during execution, not a reason to delete the stored credential.

State recommendation

Do not move the host checkpoint back to Configured and do not clear credentials. Unknown commit state or ambiguous credential attribution must fail without a resumable auth gate. If the card must react, fold only a valid unresolved caller-scoped auth gate into setup_needed.

Adapter

Protocol boundary

WASM, MCP, first-party, and native responses adapt to the same dispatch contract.

Facade

One semantic entry

A concrete processor constructs inline runtime outcomes and hides no alternate execution path.

Optional Strategy

Decoder choice only

Use existing adapter selection; add a trait only when two production decoders require dynamic selection.

No pattern ceremony

Plain functions

The fixed call sequence and ordered message extraction do not need Template Method or responsibility-chain hierarchies.

Migration rule

Adding optional provider context does not justify a migration. Before deleting the in-memory Unknown outcome, a legacy persisted-resolution fixture must prove unknown failure tags still project as bounded Unclassified failures without becoming success.

Four independently reviewable changes

Each phase starts with caller-level regression coverage and leaves a reversible compatibility boundary.

PR 1

Centralize and simplify

Pin all invocation modes, add the concrete processor, remove CapabilityInvocationResult, prove legacy persisted-tag replay, then remove Unknown across host-runtime, loop-host, and composition.

PR 2

Diagnostics and defaults

Shared diagnostics, host-owned credential enrichment, existing-kind ambiguity failures, dispatcher-owned attempt settlement, default HTTP/MCP decoding, and safe auth resume.

PR 3

Typed WASM outcome

WIT variant, legacy compatibility, six bundled guest migrations, artifact rebuilds, and transitive freshness coverage.

PR 4

Product projection and cleanup

Optional setup_needed overlay, removal of string-error parsing, removal of parallel diagnostics, and additive persistence verification.
